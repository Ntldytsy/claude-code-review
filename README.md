# code-review

多 agent 对抗性代码审查与交付检查的 Claude Code 插件。

从一次真实的全量审查中总结而来：多个 agent 按不同维度并行找问题，**再由独立的验证员逐条尽力证伪**——只有能推演出具体失败场景的才留下。那一轮 23 条发现里 2 条被证伪，避免了改错代码。

## 它解决什么

| 直接问 AI | 这套 |
|---|---|
| 一个上下文塞全部代码，越读越钝 | 每个 agent 独立上下文，只管一个维度 |
| **自己报的问题自己觉得都对** | **验证员是另一个 agent，默认立场「不成立」** |
| 散文输出，得人肉读 | 结构化输出，可程序过滤 |
| 容易只沿一条思路走 | 多维度互相看不见彼此，覆盖更宽 |

## 安装

```
/plugin marketplace add Ntldytsy/claude-code-review
/plugin install adversarial-code-review@ntldytsy-skills
```

命令行等价写法：

```bash
claude plugin marketplace add Ntldytsy/claude-code-review
claude plugin install adversarial-code-review@ntldytsy-skills
```

> ⚠️ **别用旧名 `code-review` 装。** 它与 Claude Code 官方的同名插件冲突——会**静默装成官方那个**，
> 输出和装成功一模一样，不会有任何提示。0.1.0 起改名 `adversarial-code-review` 避开。
> 实测不加 `@ntldytsy-skills` 也能正确解析；写上更保险，防止日后别的市场出现同名。

## 使用

装好后直接说人话，不用记路径：

```
跑一轮代码检测
上线前帮我过一遍
只查有没有重复扣费的地方
这次审查要花多少额度？
```

要显式点名时用 `adversarial-code-review:code-review`（Claude Code 另有一个内置的 `code-review`，
直接敲 `/code-review` 命中的是内置那个，不是本插件）。

## ⚠️ 成本

**1 个 agent ≈ 8–12 万 token。** 插件内置了成本约束：不指定规模时会**先问你起几个 agent 并报出预估**，不会自作主张放大。

**agent 数 = 维度数 × 2**（每维度 1 个找手 + 1 个验证员）。下表第三列才是计费依据。

| 规模 | 维度数 | **实际 agent 数** | 预估消耗 |
|---|---|---|---|
| 不起 agent（默认） | — | **0** | ~5 万 |
| 轻量 | 1 | **2** | ~20 万 |
| 标准 | 2 | **4** | ~40 万 |
| 全量 | 3 | **6** | ~60 万 |
| 跑满默认配置 | **4**（DEFAULT_DIMS 全开） | **8** | **~80 万** |
| 默认 + `security` | 5 | **10** | ~100 万 |
| 默认 + 两个可选维度 | 6 | **12** | **~120 万** |

⚠️ **直接跑未修改的 `workflow.js` 是最后一行（8 agent ≈ 80 万），不是「标准」。**
`DEFAULT_DIMS` 恰好 4 个维度，和表里「标准」那个 4（agent 数）不是一回事。

日常小改动走「不起 agent」就够了。

## 内容

```
skills/code-review/
├── SKILL.md                 入口：成本表、规模选择、流程、纪律
├── workflow.js              通用工作流脚本模板（4 处按项目填）
└── reference/
    ├── playbook.md          方法论全文：分层验证、部署骨架、15 条反模式、检查清单
    └── stack-mapping.md     PHP / Node.js / 纯 HTML / Vue2 的具体命令映射
```

分层加载，实测占用（`claude plugin details` 的估算）：

| | 开销 | 什么时候付 |
|---|---|---|
| 常驻 | **~190 token** | 每个会话，只有技能描述 |
| 触发时 | ~3.5k token | 技能被调用时才加载 `SKILL.md` |
| `reference/` 下的大文件 | 按需 | 只在真要查方法论 / 技术栈命令时读 |

**`SKILL.md` 并不常驻**——常驻的只有那段描述。

## 几条核心主张

- **先锚定真源**：确认要审的代码 == 线上正在跑的那份。这步跳过，后面全废。
- **编译通过 ≠ 正确**：构建成功只证明语法没错。UI 改动要么真跑起来看，要么明说没验证。
- **验证要能证伪自己**：只会「通过」的验证等于没验证——**包括你自己新加的门禁**，它误报的代价可能比不加更大。
- **交付后要有一条「只有新版本才有的可观测差异」**：没有它，你只知道「站还活着」，不知道「新代码生效了」。
- **减比加优先**：抽公共模块时只搬现有逻辑，别顺手加兜底。

## 注意

- `workflow.js` 有 4 处 `【按项目填】`（PATHS / PROJECT / KNOWN / DIMS）。
  **`PATHS` / `PROJECT` 没填会直接中止**，不会让一整轮 agent 拿着占位符白跑；
  `KNOWN` 没填按「首次跑、无已知问题」处理；`DIMS` 换技术栈时必须换。
- 换技术栈**必须替换 DIMS 的重点清单**——默认维度假设了「ORM + 事务」的后端和「SPA 生命周期」的前端。
- **两个维度默认不开**，按需用 `args.extraDims` 追加（每个 +2 agent）：
  - `security` —— 项目涉及**凭证/密钥、支付、他人个人信息、多租户隔离、文件上传、对外开放的写接口**时**必开**。
    安全问题的特征就是没有症状，等出现症状损失已经发生，所以它是准入维度而不是「有症状再查」。
  - `reuse-consistency` —— 同一个需求改了多处、或新功能是照着已有功能做的时候开。
    它查的不是重复代码，是「同一件事被写成了多种样子」（按钮一处主色一处默认、文案不一致），默认维度一条都抓不到。
- `reference/stack-mapping.md` **第 1 节是 15 条修正**，务必先看：后面各节是 agent 原始产出，其中有标着 `confident` 却跑不通的命令。
