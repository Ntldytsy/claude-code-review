# code-review

多 agent 对抗性代码审查的 Claude Code 插件：**只审查并给修改方案，不改代码、不部署。**

从一次真实的全量审查中总结而来：多个 agent 按不同维度并行找问题，**再由独立的验证员逐条尽力证伪**——只有能推演出具体失败场景的才留下。那一轮 23 条发现里 2 条被证伪，避免了改错代码。

## 它解决什么

| 直接问 AI | 这套 |
|---|---|
| 一个上下文塞全部代码，越读越钝 | 每个 agent 独立上下文，只管一个维度 |
| **自己报的问题自己觉得都对** | **验证员是另一个 agent，默认立场「不成立」** |
| 散文输出，得人肉读 | 结构化输出，可程序过滤 |
| 容易只沿一条思路走 | 多维度互相看不见彼此，覆盖更宽 |

## 安装

```
/plugin marketplace add Ntldytsy/claude-code-review
/plugin install adversarial-code-review@ntldytsy-skills
```

命令行等价写法：

```bash
claude plugin marketplace add Ntldytsy/claude-code-review
claude plugin install adversarial-code-review@ntldytsy-skills
```

> ⚠️ **别用旧名 `code-review` 装。** 它与 Claude Code 官方的同名插件冲突——会**静默装成官方那个**，
> 输出和装成功一模一样，不会有任何提示。0.1.0 起改名 `adversarial-code-review` 避开。
> 实测不加 `@ntldytsy-skills` 也能正确解析；写上更保险，防止日后别的市场出现同名。

## 使用

装好后直接说人话，不用记路径：

```
跑一轮代码检测
上线前帮我过一遍
只查有没有重复扣费的地方
这次审查要花多少额度？
```

要显式点名时用 `adversarial-code-review:code-review`（Claude Code 另有一个内置的 `code-review`，
直接敲 `/code-review` 命中的是内置那个，不是本插件）。

## ⚠️ 成本

**1 个 agent ≈ 8–12 万 token，agent 数 = 维度数 × 2**（每维度 1 个找手 + 1 个验证员）。
不指定规模时，插件会**先问你起几个 agent 并报出预估**，不会自作主张放大。

| 想要 | 怎么传 | agent 数 | 预估 |
|---|---|---|---|
| 不起 agent（默认） | — | 0 | ~5 万 |
| 只查一个维度 | `only: ['backend-bugs']` | 2 | ~20 万 |
| 只审这次改动 | `diffBase: 'main'` | 随维度 | 通常明显更省 |
| 默认全开 | （什么都不传） | **8** | **~80 万** |
| 默认 + security | `extraDims: ['security']` | 10 | ~100 万 |

⚠️ 什么都不传 = 8 个 agent ≈ 80 万，不是「标准」档。完整成本表、规模选择规矩只在
[`SKILL.md`](skills/code-review/SKILL.md) 维护一份。脚本启动时会 `log` 本轮实际维度数和预估。

日常小改动走「不起 agent」就够了。

## 内容

```
skills/code-review/
├── SKILL.md                 入口：成本表、规模选择、流程、纪律
├── workflow.js              工作流脚本；args 就能跑，不用改源码
└── reference/
    ├── playbook.md          方法论：分层验证、修改方案格式、反模式、检查清单
    ├── stack-mapping.md     技术栈索引 + 没列出的栈怎么自己补
    └── stack-{python,php,node,html-jquery,vue2}.md   各栈命令（只读命中的那个）
evals/                       带标准答案的靶子：3 个真 bug + 1 个诱饵，改脚本后回归用
```

分层加载：常驻只有技能描述；触发时才加载 `SKILL.md`；`reference/` 按需读。

## 几条核心主张

- **先锚定真源**：确认要审的代码 == 线上正在跑的那份。这步跳过，后面全废。
- **验证要能证伪自己**：只会「通过」的验证等于没验证。验证员默认立场「不成立」，写不出具体失败场景的发现不留。
- **「读不出结论」单列**：不被压成「不成立」，也不被当成「没问题」，是人工复核的第一优先级。
- **方案只写必要的改法**：减比加优先，不顺手重构、不加走不到的兜底；有多种改法就并列取舍；改表、产品语义、成本策略、抽公共模块一律放在方案顶部交人拍板；既有的无关死代码只提醒、不进改法。
- **编译通过 ≠ 正确**：UI 改动要么真跑起来看，要么明说没验证。

## 注意

- `workflow.js` 靠 `args` 传 `paths` + `project` 即可运行；**两者没填会直接中止**，不会让一整轮 agent 拿着占位符白跑。
  `known` 没填按「首次跑、无已知问题」处理。
- **找手 agent 没返回会被单独标出（`失败维度`）**，不会被当成「该维度 0 条 = 干净」。
- 跨维度重复的发现会按「同文件、行号 ±3」合并，其他维度记在 `alsoFoundBy`。
- 返回值里有现成的 markdown `报告`；脚本写不了文件，请先落盘再出修改方案。
- 换技术栈**必须替换 DIMS 的重点清单**——默认维度假设了「ORM + 事务」的后端和「SPA 生命周期」的前端。
- **两个维度默认不开**，用 `args.extraDims` 追加（每个 +2 agent）：
  - `security` —— 涉及**凭证/密钥、支付、他人个人信息、多租户隔离、文件上传、对外开放的写接口**时**必开**。
    安全问题没有症状，等出现症状损失已经发生，所以它是准入维度。
  - `reuse-consistency` —— 同一个需求改了多处、或新功能照着已有功能做时开。
    它查的是「同一件事被写成了多种样子」，默认维度一条都抓不到。
  - `llm-async` —— 调用大模型生成内容、或有慢的异步生成任务时开。查 Prompt 占位符静默缺失、重启后残留的「生成中」僵尸、哨兵值类型。
- 各栈命令文件开头写明了**哪些实际跑过、哪些没跑过**；没跑过的首次用到时请先在自己项目里验一次。
