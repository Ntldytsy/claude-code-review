# 代码审查 Playbook

> 本文是 `adversarial-code-review` 插件的方法论参考，由 `SKILL.md` 按需引用。想脱离插件使用，可整个 `reference/` 复制到项目 `docs/` 下。

## 怎么用这份文档:先做替换,再开工

这份文档从一次实战总结而来(Python 后端 / Vue 前端 / 有付费外部调用)。
**方法论通用,命令与形态不通用。** 下面五类内容照抄会失效或误报,必须先替换:

| 要替换的 | 出现在 | 不替换的后果 |
|---|---|---|
| **语言/工具链命令**(静态检查器、依赖目录排除项、搜索的文件后缀) | §2 §4 | 搜索扫 0 个文件 → 被当成「确认无影响」 |
| **前端请求通道**(XHR / fetch / 两者) | §4 | 打桩静默失效 → 打到真实后端 |
| **「不可逆副作用」是什么**(付费调用 / 发消息 / 写生产数据 / 长时任务) | 全文 | 判严重度的标尺失准 |

文中 `【按项目填】` 是**必须动**的地方。没标记的地方也可能需要按上表映射。

## 0. 核心原则(其余都是推论)

| 原则 | 展开 |
|---|---|
| **先锚定真源** | 动手前确认「我审的这份 == 线上真在跑的那份」。真源错了,后面全废。 |
| **理解要宽,改动要窄** | 读得比改的多一个数量级;改动只碰必要那几行。 |
| **编译通过 ≠ 正确** | 构建成功只证明语法没错。要么真跑起来看,要么明说「我没验证过 X」。 |
| **验证要能证伪自己** | 每层都要有「如果我错了,这层会不会告我」的能力。只会通过的验证等于没验证。**包括你自己新加的门禁——它误报的代价可能比不加更大。** |
| **减比加优先** | 过度设计本身就是缺陷。抽公共模块时**只搬现有逻辑,别顺手加兜底**。 |
| **数据反常先停,不重试** | 返回自相矛盾/为空 = 工具或解析坏了。用最短命令重新锚定一次,绝不用假数据填空缺。 |

## 1. 锚定真源

**要回答的只有一个问题:我即将审的代码,和线上正在跑的那份是同一份吗?**

### 分支 A:有版本库 + CI/CD 部署(绝大多数项目)

锚定 = **比对「线上实际部署的版本」与「你本地 HEAD」**:

- 找到线上暴露的版本标识:构建注入的 commit/version 接口、镜像 tag、流水线最近一次成功部署的 commit。
- 与本地 `git rev-parse HEAD` 比对。
- **不一致就先说清差异**(线上落后 N 个提交 / 你在一个没部署的分支上),再决定审哪份。

> 这一步最常见的失手不是「找错代码」,而是**在一个根本没部署的分支上审得很认真**。

### 分支 B:真源在远端主机被直接编辑(少见但存在)

若服务端代码是登机器改的、仓库已漂移,**先拉一份到临时目录**再审:

```bash
ssh <host> 'cd <代码目录> && tar cz \
  --exclude=【按项目填:依赖目录，如 venv/node_modules/vendor】 \
  --exclude=【按项目填:构建产物与缓存】 \
  --exclude=【按项目填:密钥文件，如 .env】 \
  --exclude=【按项目填:媒体/上传目录】 .' > /tmp/src.tgz
mkdir -p <临时目录> && tar xzf /tmp/src.tgz -C <临时目录>
```

### 两个分支都要守的规矩

- **本 skill 不改被审文件。** 临时拉取的那份**只读、审完即弃**——否则你会得到一份改在 `/tmp` 里、从没进过版本库的改动。
- **按真实来源判断身份，别靠文件夹名猜**：文件夹名、显示名、仓库 path 经常错位。用 `git remote get-url origin`、`git rev-parse HEAD` 确认；批量匹配时也要考虑命名变体（`*backup`、`*-back`）。
- 脚本里 `cd` 到临时目录后要判断是否成功，或直接用绝对路径——`cd` 失败后续命令会在错误目录执行。
- 磁盘上「已作废但还没删」的目录是最大陷阱:看起来能读,内容是旧的。开工前先确认哪些目录不该读。

**产出**:一句话写清「本轮审查的代码在 `<路径>`,对应 commit/版本 `<x>`,与线上一致/不一致(差异是…)」。

## 2. 并行:起审查工作流 + 自己通读

这两件事**同时**做:工作流(§3)在后台跑 agent 找问题;你自己**只读地**通读全部相关代码。

### ⚠️ 硬纪律:工作流跑期间绝不改文件

验证员 agent 要核对行号。你一改,它们读到的代码与找手报的行号错位 → **真问题会被误判成「行号对不上 → 不成立」**。
先读完、先规划,结果回来再统一改。

### 通读时同步做两件事

**① 影响面扫描(带符号名搜索)**

凡改动会改变「别人依赖的形状」——函数签名、返回结构、字段增删改名、数组顺序/下标、共享常量、全局样式类名——**先用一条带符号名的搜索找出所有消费方**:

```bash
rg -n 'someFunction|SOME_CONSTANT|oldFieldName' <src>       # 优先 rg：自动读 .gitignore、跳二进制
# 只有 grep 时：
grep -rIn 'someFunction\|SOME_CONSTANT\|oldFieldName' <src> \
  --exclude-dir={.git,node_modules,dist,build,vendor}
```

> ⚠️ **别给搜索加文件后缀过滤器**,除非你确认它覆盖了本项目的全部后缀。
> 写死 `--include='*.py'` 到了 Go/Rust/TS 项目会**扫 0 个文件**——那不是「没有消费方」,是「没搜」。
> **命中数为 0 时先自检过滤器,再下结论**;否则这条纪律会把假阴性升级成「我确认没影响」,正好制造它最想拦掉的返工。

**② 把执行计划落盘**

把「每条改什么、哪个文件哪一行、怎么改」写进一个临时 md。长会话里上下文会被压缩,这份计划是唯一不会丢的东西。

## 2.5 默认路径:不起 agent 怎么审

成本表里「不起 agent」那档是**默认**,不是兜底。多数改动——单个 bug、一个模块的小改、
「这段写得对不对」——起工作流是纯浪费。这一节就是那档的操作清单,**不用读 §3**。

### 先判断:这次该不该起 agent

**不起**:改动能一屏看完或集中在 1–2 个文件 · 是你自己刚写完的代码 · 只想确认某一类问题
(「有没有漏 await」「这个 if 是不是多余」)。
**值得起**:接手陌生代码库 · 跨模块的大改 · 久没审过的存量代码 · 上线前的最后一轮。

> **审自己刚写的东西是最容易超支的场景**——动手前先问值不值。

### 五步

1. **锚定真源**(§1 一步都不能省):一句话说清审的是哪份、对应哪个 commit、与线上是否一致。
2. **拿到改动面**:`git diff`(未提交)或 `git diff <base>...HEAD`(整条分支)。
   **先看 diff、再看上下文全文**——diff 告诉你改了什么,全文告诉你改动落在什么前提上。
3. **影响面搜索**(§2 ①):形状类改动用带符号名的搜索找消费方;**命中 0 时先自检过滤器再下结论**。
4. **按维度自查**:维度清单直接用 `workflow.js` 里 `DEFAULT_DIMS` 的 `focus`。
   **那几段不是给 agent 专用的,人照着过一遍同样有效**;按本项目技术栈换掉不适用的条目
   (见 `stack-mapping.md`)。
5. **跑分层验证的前两层**(§4):语法 + 静态检查。这层最常抓到「改的过程中自己新引入的 bug」,
   不起 agent 也别跳。

### 这条路径天然缺什么

不起 agent = **没有对抗验证**,自己报的问题自己觉得都对。两个补偿手段:

- **每条结论都按 `failure` 的标准写一遍**:「什么输入 / 什么时序 → 什么错误结果」。
  写不出具体失败场景的,大概率不是真问题——这正是验证员用来毙掉假阳性的同一把尺。
- **拿不准的标「存疑」,别压成「没问题」**,也别压成「是问题」(同 §3 的三态判定)。

## 3. 多 agent 审查工作流

### 为什么值得,而不是直接问 AI

| | 直接问 | 多 agent |
|---|---|---|
| 上下文 | 一个窗口塞全部代码,越读越钝 | 每个 agent 独立窗口,只管一个维度 |
| **自我确认偏误** | 自己报的问题自己觉得都对 | **验证员是另一个 agent,默认立场「不成立」** |
| 输出 | 散文,得人肉读 | JSON,可程序过滤/统计 |
| 覆盖 | 容易只沿一条思路走 | 多维度互相看不见彼此,覆盖更宽 |

实测价值:报上来的问题里总有一部分「看着很像 bug 其实不是」,对抗验证专门用来毙掉它们。

### 运行前提

脚本里的 `phase()` / `pipeline()` / `agent()` / `log()` / `args` 是**宿主 harness 注入的全局**(Claude Code 的 Workflow 工具),不是标准 JS。

- **有这个能力**:把 §3 脚本存到 `.claude/workflows/code-review.js`,然后对 AI 说「跑 code-review 工作流,`args.paths` 用 `{...}`」。结果以结构化对象返回;每个 agent 的原始返回值落在工作流转录目录的 `journal.jsonl`(工具返回结果里会给出该目录路径)。
- **没有这个能力**:整节退化为手工版——把 `workflow.js` 里 `DIMS` 的 prompt 分别开成几个独立子 agent/会话,再把它们的输出喂给一个「对抗验证员」会话。**结构比工具重要**:多维度 + 独立验证 + 结构化输出,这三点手工也能做到。

### 规模:别贪

| 规模 | 结果 |
|---|---|
| N 个找手 + **每维度 1 个批量验证员** | ✅ 一次跑成,十几分钟 |
| 每条发现各配 2 个验证 agent(=几十个) | ❌ 撞用量上限,大批 agent 挂掉,token 全废 |

**换算:`agent 数 = 维度数 × 2`**(每维度 1 个找手 + 1 个验证员)。`workflow.js` 默认 4 个维度 = 8 个 agent。
规模选择、`args.only/skip/diffBase` 的省钱用法、额度估算**只在 `SKILL.md` 的成本表维护一份**，这里不重复。

验证员**一次收下该维度全部发现、逐条判定**,不要一条一个 agent。
**跑完别急着杀**:慢是正常的。杀之前先确认结果文件里已有返回值——曾经在找手跑了 6 分半、就差返回时按停止,全部作废。

### 脚本:见 `workflow.js`

脚本本体在 `workflow.js`(skill 内路径 `skills/code-review/workflow.js`,相对本文件是 `../workflow.js`)。
**这里不再重复一份** —— 同一份脚本存两处必然漂移,而漂移时读文档的人不会知道自己读的是旧的那份。

用法:`args` 直接传 `paths` / `project` 就能跑(参数表见 `SKILL.md` 2b)；想固化成项目版本再复制到 `.claude/workflows/code-review.js` 改占位符。

脚本里有四个设计点,改的时候别改掉:

- **判定按 `index` 回填,不按 `title` 匹配** —— 验证员会改写标题,按标题匹配会让判定大面积落空(下一节就是这个坑的实战记录)。
- **验证员一次收下该维度全部发现、逐条判定** —— 不要一条发现配一个 agent(见上面「规模:别贪」)。
- **`EXTRA_DIMS` 里两个维度默认不开**:`security`(涉凭证/支付/个人信息/多租户/上传/公开写接口时**必开**)、
  `reuse-consistency`(同一需求改多处、或新功能照着旧功能做时开)。传 `args.extraDims` 追加,每个 +2 agent。
- **找手没返回 ≠ 该维度干净**：脚本把它记进 `失败维度`，汇总里单独告警；别改回「空数组当 0 条」。
- **`PATHS` / `PROJECT` 里的 `【按项目填】` 没替换就会直接中止** —— 占位符没填还能跑起来的话,等于一整轮 agent 拿着不存在的路径白跑十几分钟。`KNOWN` 没填则按「首次跑、无已知问题」处理,不中止。

### 拿到结果后:先质疑结果本身

**不要直接相信汇总数字。** 去 `journal.jsonl` 拿 agent 的**原始返回值**核对一遍。

真实踩过的坑:汇总逻辑按 `title` 匹配判定,而验证员会改写标题 → 23 条里 14 条被标成「未判定」,其实验证员全判了,**差点漏掉一条最严重的问题**。(`workflow.js` 已改成按 `index` 回填。)

**怎么核 `journal.jsonl`:先看结构,再写过滤器。**
这里**不给现成的 `jq` 一行流**——journal 的字段名随 harness 版本变,照抄一条过不去的命令,
比没有命令更糟(它会返回空,而空很容易被读成「没问题」)。按这个顺序走:

```bash
head -c 600 <转录目录>/journal.jsonl     # 先看一条记录的真实结构，再决定按什么字段过滤
```

拿到真实字段名之后再按 `label`(形如 `verify:backend-bugs`)过滤取原始返回值。
**这正是 §0「数据反常先停,用最短命令重新锚定」的同一条纪律。**

### 四个桶,四种处理

`workflow.js` 返回的不是「真/假」两堆,是四堆——**混起来看会漏掉最该看的那一堆**:

| 桶 | 含义 | 怎么处理 |
|---|---|---|
| **确认** | 验证员读了代码、能推演出失败场景 | 按 A/B/C 分级进修复清单 |
| **存疑**(读不出结论) | 读了,但证据不足以判定(缺上下文/依赖运行时配置/要跨仓库) | **人工复核的第一优先级**——它是唯一"还没有结论"的一堆 |
| **证伪** | 验证员确认被挡住 / 不可能 / 纯风格 | **抽查几条**。验证员默认立场是否定,错杀的真问题不会自己冒出来 |
| **未判定** | 验证员压根没返回这一条 | 去 `journal.jsonl` 核原始返回值,不要当成"没问题" |

> 早期版本只有 true/false 两态,规则是「存疑一律 false」——**于是"我没读明白"和"我确认不成立"
> 落进同一堆**,抽查时只能随机抽。三态就是为了把前者拎出来单列。

**另外看一眼 `被截断`**:每维度最多报 8 条,超出的条数会记在这里。非 0 说明这一轮**没报全**,
要拿全就把该维度拆细再跑一轮(注意这是新的一轮 agent,重新算钱)。

### 结果回来之后:先落盘,再考虑换会话

一轮审查跑完,主上下文已经吃进大量 agent 输出。**接着在同一个会话里动手改代码,
等于在一个已经很重的上下文里做最需要精确的事**。
先把结论(含还没核的「存疑/未判定」)写进一个 md 落盘,再 compact 或换会话去改。

## 4. 分层验证

**每层都要能证伪自己。** 只会「通过」的验证等于没验证。

| 层 | 手段(按项目替换命令) | 这层能抓什么 |
|---|---|---|
| 语法 | Python `compileall` / TS `tsc --noEmit` / Go `go build` / Rust `cargo check` | 打错字 |
| **静态** | **Python `pyflakes`/`ruff` · JS `eslint` · Go `go vet`+`staticcheck` · Rust `clippy`** | **未定义名、未用变量——最常抓到「改的过程中自己新引入的 bug」** |
| 导入 | 真的加载一次入口模块 | 循环依赖、模块级副作用炸掉 |
| **逻辑** | **隔离环境(临时 SQLite/内存库/测试容器)跑断言** | **业务规则对不对。零外部调用、零生产副作用、可反复跑** |
| **渲染** | **真起服务 + 请求打桩 + 读 DOM/计算样式** | **UI 是否真按预期渲染——「构建通过」查不出** |

### 关键技巧

**① 编辑本身要 fail-loud**

用「精确字符串替换 + 断言命中」改代码,而不是模糊匹配:

```python
old = "<原文，逐字>"
assert old in s, f"未命中: {old[:60]!r}"     # 没命中就炸，绝不静默跳过
s = s.replace(old, new, 1)
```

**② 静态检查是抓自己新 bug 的最高性价比环节**

真实战例:`pyflakes` 抓到我把 `s, p = f()` 写成了 `s, _ = f()` 却继续用 `p`。这类错误语法检查查不出、没有测试覆盖就直接漏到线上。

**③ 隔离环境验业务逻辑**

数据库指向临时库,建表、塞假数据、直接调服务层函数断言。**零不可逆副作用**,所以可以放心测「重复触发会不会被拦住」这类带副作用的路径。

> 若项目已有 CI 与测试套件:**把这些断言沉淀成测试用例**,而不是写成一次性脚本。

**④ UI 必须真渲染;登录挡路就打桩**

进不去内页时,把网络层打桩再驱动路由。**先确认本项目走哪条通道**——XHR、`fetch`、还是两者都有;只打其中一条会**静默失效**,页面照旧打真实后端(可能打到生产、甚至触发不可逆副作用),而你后面那些「已拦住」的断言会空洞通过。

```js
window.__calls = []                       // 打桩记录：断言时读它
// 【按项目填】按 url/body 返回 { status, body }；body 用你项目的响应信封
function fixtureFor(url, body) { /* return { status: 200, body: { status: 200, data: ... } } */ }
function record(url, method, raw) {
  let body = raw
  if (typeof raw === 'string') { try { body = JSON.parse(raw) } catch (e) { /* 非 JSON 原样留 */ } }
  window.__calls.push({ url, method, body })
  return body
}

// ── XHR 通道 ──
class FakeXHR extends EventTarget {
  constructor() {
    super()
    this.readyState = 0; this.status = 0; this.statusText = ''
    this.responseText = ''; this.response = null
    this.responseType = ''; this.responseURL = ''; this.upload = new EventTarget()
  }
  open(m, u) { this._m = m; this._u = u; this.readyState = 1 }
  setRequestHeader() {}
  overrideMimeType() {}
  getResponseHeader(n) { return String(n).toLowerCase() === 'content-type' ? 'application/json' : null }
  getAllResponseHeaders() { return 'content-type: application/json\r\n' }
  abort() { this._emit('abort') }
  send(raw) {
    const body = record(this._u, this._m, raw)
    const f = fixtureFor(this._u, body) || { status: 200, body: {} }
    setTimeout(() => {
      if (f.networkError) { this._emit('error'); return }          // 让错误路径也能被断言
      this.readyState = 4
      this.status = f.status || 200
      this.statusText = this.status < 400 ? 'OK' : 'Error'
      this.responseURL = this._u
      this.responseText = JSON.stringify(f.body)
      this.response = this.responseType === 'json' ? f.body : this.responseText
      this.onreadystatechange && this.onreadystatechange()
      this._emit('load'); this._emit('loadend')
    }, 5)
  }
  _emit(type) {                                    // 同时驱动 on* 与 addEventListener 两种风格
    this['on' + type] && this['on' + type](new Event(type))
    this.dispatchEvent(new Event(type))
  }
}
window.XMLHttpRequest = FakeXHR

// ── fetch 通道 ──
window.fetch = (input, init) => {
  const url = typeof input === 'string' ? input : input.url
  const body = record(url, (init && init.method) || 'GET', init && init.body)
  const f = fixtureFor(url, body) || { status: 200, body: {} }
  if (f.networkError) return Promise.reject(new TypeError('Failed to fetch'))
  return Promise.resolve(new Response(JSON.stringify(f.body), {
    status: f.status || 200, headers: { 'content-type': 'application/json' },
  }))
}
```

**打桩自检——必须先做,否则后面全部断言无效:**

```js
// 触发应用里一个已知会发请求的操作，然后：
//   window.__calls.length > 0   → 桩生效，可以开始断言
//   window.__calls.length === 0 → 桩没接住（走了别的通道 / Service Worker / SSR）
//                                 停下来查，别继续断言，更别相信"没有请求 = 已拦住"
```

**断言行为,不只是外观**(注意每条都要能证伪自己):

- 点「危险操作」→ 确认框出现,**且 `__calls` 里没有那个请求**(先过打桩自检,这条才有意义)
- 本地改了输入 → 触发一次数据刷新 → **用户输入还在,而状态字段已更新**
- 切走页面 → 等超过一个轮询周期 → **`__calls` 长度不再增长**
- 让 fixture 返回 `status: 500` 或 `networkError` → **失败态 UI 是否可恢复**(§3 流程维度要求验的正是这个)

**⑤ CSS 搬迁的确定性验证**

样式从组件挪到全局时,注入真实标记结构、读**计算样式**逐值比对;同时验证**没有全局泄漏**——把同名元素放在作用域外,确认它没被命中。

## 5. 修改方案

**本 skill 只审查并给修改方案，不动代码。** 用户明确说「按方案改」之后才改；改完是另一个任务，不在这里。
方案遵循与「外科式改动」同一把尺：**每一行改动都要能追溯到某条确认的发现**。

方案是给「没读过这轮审查」的人看的，所以每条要自包含。**文档顶部先放一份「需你拍板」清单**，再是逐条方案。

### 顶部：需你拍板（单独拎出、醒目标注）
改表、产品语义、成本策略、**抽公共/共享模块**、**为性能牺牲简洁**——一律列在最前面，每项给选项和利弊，不替用户选。
别埋在逐条说明里：埋进去的请求容易被「顺手一起同意」，等于没真正征求。

### 逐条方案（按确认桶的发现写）
| 字段 | 写什么 |
|---|---|
| **问题** | 一句话 + `文件:行号`（验证员 `correction` 里有修正行号就用修正的） |
| **失败场景** | 什么输入/时序 → 什么错误结果（直接用 `failure`，写不出就不该进方案） |
| **改法** | 最简修法，落到具体文件/函数。**只写必要那几行**；匹配周围既有风格（不顺手改缩进/引号/命名）；不重构、不加当前环境走不到的兜底。列出**这次改动自己制造的孤儿**（变成未使用的 import/变量/函数）一并删掉 |
| **其他改法** | 有不止一种合理改法时并列写出取舍；**不静默选一个**。只有一种就省略 |
| **影响面** | 动到别人依赖的什么（签名、返回结构、字段、共享常量）+ 消费方搜索的命中清单（命中 0 时先自检过滤器）；撞见硬下标/写死常量，改法里顺带改成按 key 查找/具名常量 |
| **改完怎么验** | 对应 §4 哪一层。**bug 类先给一个能复现它的最小用例**，改之前它应当失败、改之后通过；重构类写「改前改后同一组测试都通过」。多步改动写成 `步骤 → 验证` |
| **多处一致性** | 同一件事被写成多种样子时，**指定基准实现**：以最老的、人工手写的原始代码为准；AI 生成的代码不作风格权威。局部先例自相矛盾时按语义定 |

### 排序与分桶
- **A 阻断 → B 重要 → C 建议**；同级内先放「改动小、风险低」的。相互有依赖的写明先后（如「先改 X 的签名，Y 才能改」）。
- **建议清理（非本次范围）**：既有的、与本次无关的死代码/冗余**只提醒、不进改法**——不是你这次制造的，就不顺手删。本次改动自己制造的孤儿才算本次改动。
- **待核实**：存疑和未判定的单列，**不要写成改法**。
- **不进方案**：证伪桶里的；用户已拍板「保持现状」的（附根因，避免下次重复报）。

### 诚实
方案里说得出「哪些部分我没能验证」，别把推演写成实测。

## 6. 反模式清单(都是真踩过的)

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| **搜索加了写死的文件后缀** | `--include='*.py'` 到了别的语言 → **扫 0 个文件,却被当成「确认无影响」** | 用 `rg`;命中 0 时先自检过滤器再下结论 |
| **只打桩一条请求通道** | 只换 `XMLHttpRequest`,`fetch` 项目静默走真实后端 → 可能打到生产,而「没有请求=已拦住」的断言空洞通过 | 两条都打;**先做打桩自检**确认桩真的接住了 |
| **打桩只造成功路径** | `status` 恒 200、从不触发错误 → 失败态 UI 根本没被验证 | fixture 支持 `status`/`networkError`,把「失败后能否恢复」也断言一遍 |
| **抽公共模块时顺手加兜底** | 抽复制逻辑时顺手加了降级分支,而运行环境不会走到 → 从第一天起就是死代码,几小时后整个函数被删 | 只搬现有逻辑。抽完自问:「去掉我顺手加的那部分,这个抽取还成立吗?」不成立就不该抽 |
| **信任汇总,不看原始数据** | 按 title 匹配判定 → 14/23 被标「未判定」,差点漏掉最严重那条 | 拿 agent 原始返回值核对;匹配用稳定标识(index/id) |
| **返回异常时重试** | 解析出 0 条就再跑一遍 → 浪费且污染上下文 | **停下来用最短命令重新锚定一次**(如 `head -c 400` 看文件真实结构) |
| **工作流跑到一半觉得慢就杀** | 找手跑了 6 分半、就差返回时按停止 → 全部作废 | 先确认结果文件里已有返回值再考虑停 |
| **改动落在临时拉取的副本上** | 得到一份改在 `/tmp` 里、从没进版本库的改动 | 临时副本只读、审完即弃;改动一律落在版本库工作副本 |
| **用「构建成功」暗示 UI 没问题** | 组件没注册会静默不渲染、无报错、编译照过 | 真跑起来看,或明说「我无法验证渲染,请确认 X/Y/Z」 |
| **在长会话里硬撑做大量改动** | 上下文过半后每轮都要重过全部历史 | 大改前换会话,把交接写成自包含文档 |

## 8. 什么时候该停

### 必跑,与有没有症状无关

**安全**——只要项目涉及以下任一项,安全就是**准入维度**,不是症状驱动:

> 凭证/密钥 · 支付 · 他人个人信息 · 多租户数据隔离 · 文件上传 · 对外开放的写接口

理由:**安全问题的特征就是没有症状**——注入、越权读他人数据、密钥进仓库或日志、公开写接口无鉴权,在被利用之前都不会「慢」也不会「报错」;等出现症状,损失已经发生。
至少跑一轮:鉴权与归属校验、注入与反序列化、密钥是否进仓库/进日志、越权枚举、上传文件的类型与路径校验。
**怎么跑**:`workflow.js` 的 `EXTRA_DIMS.security` 就是这个维度,默认不开,传 `args.extraDims: ['security']` 追加
(+2 agent ≈ +20 万)。**注意后端维度里的「权限与归属校验」只是其中一条,不能拿它当安全维度用。**

**自动化测试**——若项目已有 CI 与测试套件:本文档 §4 的隔离断言脚本应当**沉淀为测试用例**。
本文档的验证栈(手写断言脚本、手动打桩)本质是在**替代**测试套件;在有 CI 门禁的仓库里把它当替代品,等于劝人不要补回归网。

### 覆盖到这些就可以收工

死代码/冗余/重复 · 过度设计 · 真实缺陷(并发/事务/竞态/状态机) · 前端竞态与生命周期 · 产品流程与不可逆副作用 · 权限校验
(前两项由 `dead-code-overdesign` 维度覆盖——**若你删掉了那个维度,就要在 §7 清单里人工过一遍**。)

**另一类容易漏的**:同一个需求改了多处时,「几处用户看到的是不是同一个东西」。
它不是重复代码(那是 `dead-code-overdesign`),而是**同一件事被写成了多种样子**——
按钮一处主色一处默认、文案不一致、一处有二次确认另一处没有。默认维度一条都抓不到,
用 `EXTRA_DIMS['reuse-consistency']` 追加。

### 真正可以「有症状再做」的

性能**深挖**（基准、剖析）· 端适配/可访问性 · 大规模重构。
**但明显的性能点（N+1、能在数据层解决却在内存里循环、无谓全量扫描）默认维度会顺手报**，一律 C 级并标「简洁 vs 性能需拍板」——只提出，不擅自要求优化。

预防性铺开更多轮审查,本身就是一种过度设计。
**「暂时不值得做」和「还没做完」是两件事,要说清楚是哪一种。**
