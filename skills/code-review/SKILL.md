# 代码审查与修改方案

**本 skill 只做两件事:审查 → 给修改方案。不动代码、不部署、不发版。** 用户明确说「按方案改」才改,那是另一个任务。

## ⚠️ 第一件事:先算账,再问规模

**实测单价:1 个 agent ≈ 8–12 万 token**(三次真跑:6 agent=688k / 3 agent=211k / 5 agent=403k,
括号里都是 **agent 总数**,不是维度数)。

### ⚠️ 换算公式:**agent 数 = 维度数 × 2**

`workflow.js` 是「每个维度 1 个找手 + 1 个批量验证员」,所以维度数要 **乘 2** 才是实际 agent 数。
下表第三列才是计费依据。

| 规模 | 维度数 | **实际 agent 数** | 预估消耗 | 什么时候用 |
|---|---|---|---|---|
| **不起 agent** | — | **0** | ~5 万(只是我自己读代码的开销) | 小改动、单个 bug、「这段写得对不对」——**默认走这条** |
| **轻量** | 1 | **2** | ~20 万 | 只查一个维度(如「只看花钱的地方」)。`args.only: ['backend-bugs']` |
| **标准** | 2 | **4** | ~40 万 | 一个模块改完了想过一遍。`args.only: ['backend-bugs','flow-sanity']` |
| **全量** | 3 | **6** | ~60 万 | 大版本前、久没审过。`args.skip` 去掉一个默认维度 |
| **跑满默认配置** | **4**(DEFAULT_DIMS 全开) | **8** | **~80 万** | 接手陌生代码库,且已确认预算够 |
| 默认 + `security` | 5 | **10** | ~100 万 | 涉敏感面的项目做全量 |
| 默认 + 两个可选维度 | 6 | **12** | **~120 万** | 上限。除非明确要求,不要走这档 |

> ⚠️ **直接跑未改过的 `workflow.js` = 最后一行(8 个 agent、约 80 万),不是「标准」那档。**
> `DEFAULT_DIMS` 正好有 4 个维度,别把它和表里「标准」那个 4 搞混——一个是维度数、一个是 agent 数。
> 要省就用 `args.only` / `args.skip` 选维度（不用改源码），或只传自定义 `dims`。
> 只想审这次改动：加 `args.diffBase: 'main'`，agent 只读 `git diff main...HEAD` 涉及的文件，通常显著更省。
> 脚本启动时会 `log` 一行「本轮 N 个维度 = 2N 个 agent ≈ X 万」，和你报给用户的预估对一下。

**规矩:**
- 用户没明说规模时,**先问**「起几个 agent / 要哪几个维度」,并报出预估消耗。**不要自己决定规模。**
- 除非用户明确说「全量」「彻底」,否则默认往小了起。
- 审查自己刚写的东西之前,先问值不值——这是最容易超支的场景。
- **问规模时必须一并问一句**:本项目涉及凭证/密钥、支付、他人个人信息、多租户隔离、
  文件上传、对外开放的写接口吗?涉及任一项 → 安全是**准入维度**,`security` 要算进规模
  (+2 agent ≈ +20 万),不是"有症状再查"。理由:安全问题的特征就是没有症状。
- 规模定完再用一句话对齐**范围**:审哪些路径 → 哪几个维度 → 产出什么 → **明确不审什么**。
  最后一项最容易漏,而它正是事后「你怎么没看安全」的来源。

## 流程

### 1. 锚定真源(跳过这步后面全废)

确认「要审的代码 == 线上正在跑的那份」:

- **有版本库 + CI/CD**(多数情况):比对线上暴露的版本/commit 与本地 HEAD。不一致先说清差异。
- **真源在远端被直接改**(少见):先一次 SSH 拉到 scratchpad 再审,**临时副本只读**,改动一律落回版本库工作副本。

产出一句话:「本轮审查 `<路径>`,对应 `<commit/版本>`,与线上一致/不一致(差异…)」。

### 2a. 走「不起 agent」那档(默认)

**这档不是兜底,是默认。** 操作清单在 `reference/playbook.md` §2.5:
锚定真源 → `git diff` 拿改动面 → 带符号名搜消费方 → 照 `DEFAULT_DIMS` 的 `focus` 自查 → 跑语法+静态检查。

这条路径**没有对抗验证**,所以每条结论都要按「什么输入/什么时序 → 什么错误结果」写一遍;
写不出具体失败场景的,大概率不是真问题。拿不准的标「存疑」,别压成「没问题」。

### 2b. 起工作流 + 自己通读(并行)

`workflow.js` **不用改源码就能跑**,全部靠 `args` 传:

| args | 作用 |
|---|---|
| `paths` | `{分区名: 绝对路径}`,**必填** |
| `project` | 一段话:项目做什么 / 哪些是不可逆副作用 / 团队标准,**必填** |
| `known` | 上轮已确认或已拍板不改的问题(不填会让 agent 把旧结论再报一遍) |
| `only` / `skip` | 选/去默认维度;名字拼错会直接报错 |
| `extraDims` | 追加 `security` / `reuse-consistency` |
| `diffBase` | 只审 `git diff <base>...HEAD` 的文件 |
| `dims` | 完全自定义 `[{key, role, focus}]` |

想固化成项目专属版本时,再复制到 `.claude/workflows/` 改源码里的占位符。

- **`paths` / `project` 没填会直接中止**(脚本自带守卫),不会让一整轮 agent 拿着占位符白跑。
- **两个可选维度默认不开**(在 `EXTRA_DIMS` 里,传 `args.extraDims` 追加):
  `security`(涉敏感面时必开,见上)、`reuse-consistency`(同一需求改了多处、或新功能是照着旧功能做的时候开)。
- **换技术栈必须换 `DIMS` 的重点清单**。默认那几个维度假设了「ORM+事务」的后端和「SPA 生命周期」的前端;PHP/纯 HTML 项目照跑会整段空转。→ 查 `reference/stack-mapping.md`(索引,指向各栈单独文件)。
- 改了脚本或 prompt 之后,用 `evals/` 里的靶子回归一次(约 20 万),确认审查没变钝。

**跑期间绝不改文件** —— 验证员要核对行号,一改就全错位,真问题会被误判成「行号对不上 → 不成立」。

**跑完别急着杀**:慢是正常的(agent 在真读代码)。停之前先确认结果文件里已有返回值。

### 3. 结果处理

结果分**四桶**,别混着看(为什么是四桶、每桶的完整处置见 playbook「四个桶,四种处理」):

- **确认** → 按 A/B/C 进修复清单
- **存疑**(读不出结论) → **人工复核第一优先级**,唯一"还没有结论"的一堆
- **证伪** → 抽查几条;验证员默认立场是否定,错杀不会自己冒出来
- **未判定**(验证员没返回) → 去 `journal.jsonl` 核原始返回值(实测发生过 14/23 被误标),**≠「没问题」**

- 核 `journal.jsonl` 时**先 `head -c 600` 看一条记录的真实结构再写过滤器**——字段名随版本变,照抄现成命令会返回空,而空最容易被读成「没问题」。
- 看一眼 `被截断`:非 0 说明这一轮没报全(每维度 8 条上限),要拿全得拆细维度再跑一轮(重新算钱)。
- 看一眼 `失败维度`:非空说明那个维度的**找手没返回**,这个维度根本没审——**0 条≠干净**,要重跑。
- 跨维度重复的发现已按「同文件、行号 ±3」合并,别名记在 `alsoFoundBy`,两个验证员判定冲突时原样摆出来由人定。
- 返回值里的 `报告` 是现成的 markdown。**先把它落盘**(如 `review-report.md`),再据此出修改方案(步骤 5);脚本自己写不了文件。
- 按 **A 阻断 / B 重要 / C 建议** 分组,每条给依据。
- **这三类不要自己动,一律上交用户拍板**:改数据库表结构、产品语义、成本策略。

### 4. 分层验证(每层都要能证伪自己)

语法 → **静态检查** → 加载冒烟 → **隔离环境跑断言** → **真渲染**。
用途有两个:① 验证「某条发现是否真的成立」(推演不够时);② 在修改方案里写明「改完怎么验」。

- 静态检查这层**最常抓到改动过程中自己新引入的 bug**,不要跳过。
- **「构建通过」不是验证。** UI 改动要么真跑起来看,要么明说「我没验证过 X」。

### 5. 出修改方案

对「确认」桶逐条写方案,格式(问题 / 失败场景 / 改法 / 影响面 / 改完怎么验 / 谁来拍板)、排序规则、
哪些不进方案 → `reference/playbook.md` §5。要点:

- 改法只写必要那几行,**不顺手重构、不加当前环境走不到的兜底**。
- 每条写明「改完怎么验」,且该验证在改之前应当失败。
- 存疑 / 未判定的单列「待核实」,**不要写成改法**。
- 改表、产品语义、成本策略 → 标「需人拍板」,给选项和利弊,不替用户选。
- 方案落盘(如 `review-plan.md`),方便换会话后让别人照着改。

## 几个高频踩的坑(完整清单在 playbook §6)

- **搜索别加写死的文件后缀**——换语言会扫 0 个文件,却被当成「确认无影响」。
- **前端打桩要覆盖 XHR 和 fetch 两条通道**,并先做打桩自检确认真的接住了;只造成功路径的桩测不出失败态 UI。
